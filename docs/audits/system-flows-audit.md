## 1. ملخص تنفيذي

تطبيق **بيتي** هو تطبيق إدارة منزلية مبني على Flutter + Supabase. يغطي هذا التدقيق جميع التدفقات من الإقلاع حتى أعمق العمليات. تم رصد **23 مشكلة** مصنّفة كالتالي:

| الخطورة | العدد | الوصف |
|---------|-------|-------|
| 🔴 حرجة | 5 | تسبب أعطال أو فقدان بيانات |
| 🟠 متوسطة | 9 | سلوك خاطئ أو غير مكتمل |
| 🟡 منخفضة | 9 | تحسينات وتنظيف |

## 2. خارطة رحلة المستخدم

```
[إقلاع التطبيق] → [فحص الجلسة]
    ├─ غير مسجّل → [تسجيل الدخول / إنشاء حساب]
    └─ مسجّل → [فحص المنازل]
        ├─ لا يوجد منزل → [شاشة الإعداد الأولي - Onboarding]
        └─ يوجد منزل → [الشاشة الرئيسية]
            ├─ قوائم التسوق → عرض/إضافة/تعديل/حذف
            │   └─ وضع التسوق → شراء/بحث/نقل للمخزون
            ├─ المخزون (Feature Flag) → عرض/إضافة/تعديل كمية/حذف
            ├─ المصروفات (Feature Flag) → عرض/إضافة/ملخص/أرصدة
            ├─ المهام (Feature Flag) → عرض/إضافة/إكمال/تكرار
            ├─ سجل النشاطات → عرض/تصفية/تحميل المزيد
            ├─ الإشعارات → عرض/قراءة/تفضيلات
            ├─ إعدادات المنزل → أعضاء/دعوات/أدوار
            └─ الحساب → تعديل الملف/تسجيل الخروج
```

## 7. تدفقات Offline Queue

### 7.1 البنية المزدوجة (مشكلة هيكلية)
🔴 **C-03:** يوجد **نظامان منفصلان** لقائمة الانتظار غير المتصلة:

| النظام | الموقع | التخزين |
|--------|--------|---------|
| نظام 1 | `realtime_providers.dart` → `OfflineQueueNotifier` | في الذاكرة فقط (StateNotifier) |
| نظام 2 | `offline_queue/` feature → `OfflineQueueRepository` | قاعدة بيانات محلية |

- النظام 1 يفقد جميع العمليات عند إغلاق التطبيق
- النظام 2 يحتفظ بالعمليات لكن `OfflineAwareShoppingRepository` يستخدمه
- **لا يوجد تكامل واضح بين النظامين** → قد تُفقد عمليات أو تُكرّر

### 7.2 مزامنة OfflineAwareShoppingRepository
- ✅ يفحص الاتصال قبل كل عملية
- 🔴 **C-04:** عند `updateShoppingItem` في وضع Offline، يحاول جلب العنصر الحالي من `_remoteRepository.getShoppingItemById` → **سيفشل لأنه غير متصل** → `current!` سيطرح `Null check` exception

### 7.3 homeId خاطئ في القائمة
- 🟠 **M-10:** في `OfflineAwareShoppingRepository`، يتم تمرير `homeId: itemId` بدلاً من homeId الفعلي في عمليات update وdelete وmarkPurchased

## 18. التوصيات

### الأولوية 1: إصلاح Offline Queue
1. **توحيد النظامين** في نظام واحد مبني على قاعدة بيانات محلية
2. إصلاح `homeId: itemId` → `homeId: actualHomeId`
3. حماية العمليات في Offline من `Null check` exceptions

### الأولوية 2: أمان الجلسة
1. حذف `device_token` عند `signOut`
2. إضافة Guard في Router يمنع الوصول لشاشات بـ `homeId == null`

### الأولوية 3: اتساق البيانات
1. توحيد العملة بين الواجهة والخلفية
2. إضافة خيار "انضمام لمنزل" في Onboarding
3. تبديل تلقائي للمنزل النشط عند حذف المنزل الحالي

### الأولوية 4: Feature Flags
1. حراسة المسارات (Routes) بالأعلام — وليس فقط عناصر القائمة
2. النظر في Remote Config لتغيير الأعلام بدون نشر إصدار جديد

## 19. خلاصة

التطبيق في حالة جيدة هيكلياً مع بنية نظيفة (Feature-first Clean Architecture). أخطر المشاكل تتمركز في **نظام Offline Queue المزدوج** و**حل سياق المنزل النشط**. إصلاح المشاكل الخمس الحرجة كافٍ لدخول مرحلة Beta بثقة.
